# 衡信平台市场化与路演准备路线图

> 版本：2026-09-03
> 目标：将当前“功能完整的风控研发原型”升级为“客户能够快速理解、验证、接入并采购的决策平台”。

## 一、结论

下一阶段不再以新增指标、规则或治理状态为主，而是建设 **Sales-ready MVP（市场化可销售版本）**。

当前平台的指标工厂、评分卡、规则中心、模型治理、Champion/Challenger、持续验证、授信审批和贷后闭环已经具有较强纵深。主要短板已经从“有没有功能”转向：

1. 客户不能在 10—15 分钟内沿一条业务故事看懂产品价值；
2. 演示环境数据偏空、配置页信息密度过高，能力强但第一印象复杂；
3. 缺少一个独立、标准、可压测的实时/批量决策服务入口；
4. 缺少面向客户 IT 的连接器、字段映射、Sandbox 和一键部署交付；
5. 缺少租户/环境隔离、CI/CD、运行可观测性和安全交付材料；
6. 前后端若继续堆叠功能，会受到超大模块和缺少前端自动化测试的维护约束。

## 二、建议的产品定位

首个市场版本应聚焦为：

**面向大型企业、供应链核心企业和产业金融机构的客商信用评级与授信决策平台。**

核心价值表达不应是“有 201 个指标”，而应是：

- 把外部工商司法、内部交易、财务资料统一为可追溯指标；
- 让业务人员可视化配置评分卡、规则、额度和账期；
- 在发布前完成样本回放、影响比较和独立复核；
- 对每笔决策解释“用了什么数据、命中了什么规则、为什么给出该额度”；
- 对上线后的模型漂移、组合风险和策略效果持续监控。

首批不要同时面向消费金融反欺诈、零售信贷、保险、营销等所有市场。先把“对公客商信用与授信”做成一个完整样板，再通过行业方案包扩展。

## 三、外部对标得到的共识

成熟平台并不是单卖规则引擎或模型管理，而是出售一条完整的决策闭环：

`数据/特征 -> 规则/模型 -> 决策流 -> 测试模拟 -> 发布 -> 实时/批量执行 -> 监控迭代`

- 同盾公开介绍强调规则、决策表、决策树、规则流的全生命周期，以及模型构建、部署、执行和监控；
- 百融公开介绍强调数据与特征工厂、低代码规则/评分卡/决策流编排、灰度上线、A/B 测试、动态流量和模型监控；
- SAS Intelligent Decisioning 强调可视化编排、统一模型与规则仓库、发布前测试、RBAC 治理，以及批量和实时执行一致；
- FICO 公开材料强调 DMN/决策表、策略模拟优化和面向场景的 Starter Pack；
- Camunda DMN 说明标准化决策图和决策表能让业务分析人员与开发人员共同理解和执行决策；
- MLflow Model Registry 的成熟做法是模型版本、血缘、别名、标签及从开发到生产的受控流转；
- Feast 强调训练与在线服务特征一致、时间点正确性和低延迟特征服务；
- Evidently 强调把评估、测试、漂移和生产可观测性统一起来。

## 四、建议的第 38 阶段：市场化黄金路径

建议周期：3—4 周。目标不是做一套静态宣传页，而是让真实产品具备稳定、可重复的客户演示闭环。

### 4.1 方案化首页

- 首页从通用运营台升级为“管理驾驶舱 + 场景入口”；
- 提供三个预置方案：制造业供应商准入、渠道客户授信、科创企业评级；
- 每个方案明确业务问题、使用的数据、自动化结果和量化价值；
- 不再让路演首页出现“0 单、0 资料”的空业务状态；
- 根据当前角色给出正确主动作，模型管理员不应首先被引导进入审批办理。

### 4.2 一键黄金演示

- 提供“开始演示 / 重置演示”入口，5—8 分钟完整跑通一个案例；
- 固定故事：导入企业 -> 数据完整性 -> 指标计算 -> 评分卡 -> 规则命中 -> 额度/账期 -> 审批 -> 贷后预警；
- 页面以步骤条说明“现在发生了什么、为什么重要、客户获得什么”；
- 演示中准备一个正常企业、一个人工复核企业、一个拒绝企业；
- 演示状态和业务工作状态隔离，确保每场路演可重复。

### 4.3 可解释决策路径图

- 将已有指标、评分卡、规则集、管线和授权策略组装为一张可视决策图；
- 执行某个案例时高亮实际路径、命中节点和阻断节点；
- 点击节点查看输入值、版本、输出、耗时、规则依据和证据哈希；
- 第一阶段只需实现稳定的可视化与节点配置跳转，不必立即建设完整 BPMN 编辑器；
- 后续逐步扩展为兼容 DMN 思想的拖拽式决策编排器。

### 4.4 决策价值看板

- 展示自动准入率、人工复核率、拒绝率、平均审批时长、策略命中率、额度分布、风险事件捕获率；
- 同时展示“基线策略 vs 候选策略”的业务变化；
- 清楚区分演示估算、历史事实和客户真实样本结果，禁止把模拟收益包装为实际收益；
- 支持生成一页式管理层报告，路演结束可以直接交付客户。

### 4.5 路演与试点资料包

- 形成 15 分钟路演脚本、5 分钟快速演示脚本和常见质疑应答；
- 提供客户数据字段模板、API Quick Start、试点范围、验收指标和责任清单；
- 为每个方案包提供模型卡、指标字典、策略说明、审计样例和部署架构图；
- 明确演示基线阈值不是客户正式生产政策，试点必须基于客户样本重新校准。

### 4.6 第 38 阶段验收标准

- 新客户无需讲解即可从首页进入三个方案之一；
- 15 分钟内完成一条端到端演示，过程中没有手工造数据或切终端；
- 一键重置后连续执行 10 次结果一致；
- 至少 30 笔已完成案例、3 类决策结果、1 个贷后预警、1 次模型挑战者比较可直接演示；
- 每笔决策均可追溯输入快照、指标、模型、规则、策略、输出和版本；
- 路演环境无空数据、无开发令牌文字、无技术异常暴露；
- 管理层一页报告和技术试点包可在产品内导出。

## 五、后续三阶段

### 第 39 阶段：可接入试点版本（4—6 周）

- 建立统一 `Decision API`：实时单笔、批量文件、异步任务三种模式；
- 支持幂等键、`trace_id`、决策版本固定、错误码、超时和重试边界；
- 建立字段映射向导、CSV/Excel 导入、Webhook 和 Sandbox；
- 形成输入 schema、输出 schema、示例代码和 Postman/OpenAPI 集合；
- 决策日志展示请求、结果、规则路径、耗时和可解释原因；
- 目标：客户 IT 在 1 个工作日内跑通第一笔测试决策。

### 第 40 阶段：企业生产就绪（4—6 周）

- 租户、工作空间及开发/测试/生产环境隔离；
- 配置跨环境晋级，不允许在生产直接编辑；
- OIDC/SSO、细粒度权限、客户数据范围、密钥托管和审计导出；
- API 与前端 Dockerfile、完整 Compose、CI 流水线、迁移检查和自动化发布；
- 指标包括 p95/p99 延迟、吞吐、错误率、规则命中、模型漂移和任务积压；
- PostgreSQL 生产基线、备份恢复、容量规划、压测报告和故障演练；
- 目标：完成一个客户隔离环境的标准化部署和验收。

### 第 41 阶段：开放平台与差异化（6—8 周）

- 逐步支持 DMN/决策表导入导出，以及 PMML、ONNX 或 Python 模型适配；
- 建立类似模型注册表的别名、标签、血缘和外部模型接入；
- 建立在线/离线一致的特征服务接口，保证时间点正确性；
- 建立连接器 SDK 和第三方数据源插件机制；
- 加入受控 AI 助手，用于生成规则草稿、解释差异和形成报告，但所有变更仍必须走现有四眼治理。

## 六、工程治理要求

在第 38—40 阶段同步偿还会阻碍交付的结构性债务：

- 拆分超大后端仓储和前端页面，按指标、评分卡、规则、模型、决策运行形成清晰模块边界；
- 增加前端组件测试、关键用户流程 E2E、API 契约测试和性能回归；
- 建立 CI 门禁：格式、类型、单元测试、迁移、构建、依赖漏洞和镜像扫描；
- 避免继续向单个 `repository.py`、`types.ts`、`App.tsx` 和大页面组件堆叠功能；
- 继续坚持不可变快照、四眼复核和不伪造监督证据的现有治理原则。

## 七、商业验收指标

试点阶段应采集客户基线后再确定正式目标。建议至少衡量：

- 策略配置到可验证版本的时间；
- 单笔决策 p95 延迟和批量吞吐；
- 自动决策率、人工复核率和异常回退率；
- 平均审批时长与补件次数；
- 规则/模型变更从提出到发布的周期；
- 高风险事件捕获率、通过客户后续坏账/逾期表现；
- 每笔决策完整可解释和可审计覆盖率；
- 客户 IT 首次接入耗时和新方案复制耗时。

所有对外收益表述应按“当前基线、试点实际、目标情景”三栏展示，不使用未经客户样本验证的固定 ROI 数字。

## 八、暂不优先事项

- 不继续以指标数量作为主线扩张；
- 不优先做泛化大模型聊天入口；
- 不在没有真实客户数据前声称模型效果或坏账下降比例；
- 不立即建设覆盖所有行业的通用平台；
- 不在没有决策服务和部署底座前投入大量时间制作复杂动画或纯视觉大屏。
